# Repository layout

This repo stores "source changes + patches + platform differences" only. It never carries the full upstream
sm64coopdx sources and never carries a ROM. At build time `install.sh` clones the upstream sources and layers these
changes on top.

```
src/                  modified files, full copies, paths **exactly mirroring** upstream (the single edit source)
patches/NNNN-group-role.patch  **all flat; the four-digit number is the application order**:
                      0001-build-and-config.patch build switches / 0002-rom-assets.patch ROM reading / 0003-text-core.patch text core
                      0004-dialog.patch dialogs / 0005-menus.patch menu UI / 0006-asset-overlay.patch asset overlay
                      0007-djui-frontend.patch optional frontend / 0008-android.patch Android platform delta
                      (language strings / config entries are not patches, see scripts/add_{lang_strings,cn_config}.sh)
patches/cn_extra/     files that do not exist upstream, full copies, paths mirroring upstream
platform/             per-platform / per-package patches and build scripts
scripts/              patch generators + local self-test tools (not run by CI)
.github/workflows/    CI: one build.yml, five jobs (three desktop platforms + Android)
docs/                 design notes (LAYOUT.md 中文 / LAYOUT.en.md English)
upstream.txt          upstream repo and commit the patches are based on (the authoritative baseline)
```

## Deciding "modified" vs "new"

Whether a file counts as modified or new can only be decided against the baseline, never from local `git status`:

```bash
git cat-file -e <baseline commit>:<relative path>     # exists ⇒ modified (src/); missing ⇒ new (cn_extra/)
```

A file showing as `M` in a local fork does not mean upstream has it; conversely, a file that exists upstream but not
in the localised upstream also has to be confirmed against the chosen baseline.
`upstream.txt` declares four baselines: `repo` / `cn-repo` / `android` / `android-cn-repo`.

## src/

Mirrors the upstream directory structure and holds **only modified files**. Untouched files do not belong here.

```
sm64iquedx/src/src/game/print.c          ← upstream src/game/print.c
sm64iquedx/src/src/menu/intro_geo.c      ← upstream src/menu/intro_geo.c
sm64iquedx/src/Makefile                  ← upstream root Makefile
```

Rules:

1. **The path is the target path.** A relative path under `src/` is appended directly to the upstream root, with no
   intermediate layer.
2. **Whole files only.** What is stored is the complete post-edit file, not a fragment, so opening it in an editor
   gives something that reads and compiles.
3. **Only modified files.** The criterion is "byte-identical to the baseline upstream"; identical files never go in.
4. **This is the single edit source.** Change code in `src/` first; `patches/` is generated by scripts and must not
   be hand-edited.
5. **New files do not go into `src/`** — they go into `patches/cn_extra/`.

## patches/cn_extra/

Files that do not exist upstream are stored as full copies; their internal paths still mirror the upstream root:

```
patches/cn_extra/src/game/cn_font.c       → upstream src/game/cn_font.c
patches/cn_extra/src/game/cn_tex.c        → upstream src/game/cn_tex.c
patches/cn_extra/text/cn_dialogs_cn.inc.c → upstream text/cn_dialogs_cn.inc.c
patches/cn_extra/lang/Chinese.ini         → upstream lang/Chinese.ini (the PC upstream has no Chinese)
```

- They are not turned into `.patch` files: new files are usually large glyph tables or generated artefacts where a
  text diff is meaningless, and `git apply` would fail on context drift anyway.
- The directory mixes hand-written sources with **generated artefacts** (`cn_data/*.h`, `cn_intro_data.c`,
  `text/cn_*.inc.c`). After changing a generator, resync the artefacts instead of editing them by hand.
- Application is **per-file gap filling, never overwrite**: skip if the target already exists (`copy_extras()` in
  `apply_patches.sh`). The localised Android build ships its own `lang/Chinese.ini`, and a blanket `cp -R` would
  clobber it with the PC version.

## patches/NNNN-group-role.patch

- Naming: `patches/NNNN-group-role.patch`, flat, no subdirectories. `NNNN` is a global patch number and **it is the
  application order** (`sort` gives the order). The middle segment is a group name (`build` / `rom` / `text` /
  `dialog` / `menus` / `assets` / `frontend` / `platform`) that exists for human readers only, never for locating
  files. Optional groups are selected by filename glob, so no directory is needed: `--frontend` → `0007-*.patch`,
  android targets → `0008-*.patch`. Consequently "which patches belong to an optional group" never needs a separate
  list, and adding a group is just adding a file with a larger number. A file may appear in exactly one group, and
  the groups must cover the whole `src/` delta — `gen_all_patches.sh` asserts this against the full diff on every
  run.
- 8 patches: `0001-build-and-config.patch` build switches / `0002-rom-assets.patch` ROM reading /
  `0003-text-core.patch` text and glyph core / `0004-dialog.patch` dialogs / `0005-menus.patch` menu UI /
  `0006-asset-overlay.patch` iQue texture and geometry overlay / `0007-djui-frontend.patch` optional frontend /
  `0008-android.patch` Android delta. The per-file breakdown is in the table in `patches/README.en.md`.
- The old per-directory structure (`01-build/` … `08-platform/`) is **not allowed** to reappear under `patches/`,
  and filenames must follow "four-digit number-group-role": the pre-split `0001-src-overlay` / `0002-djui-frontend` /
  `0005-android` overlap with current patches, and old directories would make the same change be read twice, so both
  would be applied twice (both `gen_all_patches.sh` and `apply_patches.sh` error out).
- Always `git diff` format with paths relative to the upstream root (`a/src/...`).
- Must apply cleanly with `patch -p1` or `git apply -p1` on the baseline named in `upstream.txt`.
- `0001`~`0007` are **generated from `src/` in one shot by `scripts/gen_all_patches.sh`**; `0008-android.patch` is
  generated by `scripts/gen_platform_patches.py`. None are written or edited by hand.
- Run `git apply --check` before applying; when a baseline other than the declared one is selected, patches may be
  skipped and `src/` used to overwrite the final state directly.
- **One shared patch set and one platform patch**: PC and both Android upstreams share `0001`~`0007`, and both
  Android targets share `0008`. Do not copy a whole set for one upstream, and do not add a per-upstream platform
  patch — context drift is resolved with insertion scripts instead, see the next section. The split axis is
  **responsibility** (who consumes this data), not upstream.

## Language strings: script insertion, not patches

`lang/*.ini` only needs two added strings (`CHINESE_TEXT_PACK` and `Chinese` in the language list), but every
upstream's ini has different line numbers and stock entries (the localised Android build already ships
`Chinese = ...`). Generating one ini patch per target would grow with every upstream, and each upstream line change
would force regenerating all of them.

So instead: **the whole `lang/` prefix is excluded from every group** (filtered out by the generator, not by the
applier's `--exclude`), and strings are inserted by key at apply time with `scripts/add_lang_strings.sh`.

```bash
scripts/add_lang_strings.sh <upstream root> [--check]
```

| Behaviour | Detail |
| --- | --- |
| Key already present | Skipped (matched with `^KEY[[:space:]]*=`) |
| Anchor present | Inserted after the anchor line, so section membership is correct by construction |
| Anchor missing | Errors out instead of guessing |
| Scope | Only `lang/English.ini` and `lang/Chinese.ini`; other language files untouched |

Changing the wording only means editing two constants in the script; no patch needs regenerating. `--check` reports
without writing; one run against the PC baseline yields a file byte-identical to `src/lang/English.ini`.

## Platform delta patch: 0008-android.patch (shared by both Android targets)

One patch, 3 files (`Android.mk`, `Makefile`, `src/pc/pc_main.c`), covering only what the shared patches cannot:

1. **The two context-drift files**: `Makefile` (in `0001-build-and-config.patch`) and `src/pc/pc_main.c` (in
   `0002-rom-assets.patch`). They are skipped with `--exclude` while applying `0001`~`0006`, and the platform patch
   supplies their three-way-merged final state.
2. **The macro injection in `Android.mk`**: ndk-build does not read `Makefile`, so `-DSM64COOPDX_CN_TEXT=1` must be
   added to `LOCAL_CFLAGS`; otherwise the whole localisation is compiled out.

### Why the third drift file, `configfile.c`, is not in a patch

It is equally `--exclude`d, but its final state comes from `scripts/add_cn_config.sh` inserting those 6 lines (3
`configChineseText*` declarations + 3 `chinese_text*` config-table entries). Reason: stock Android upstream and the
localised Android upstream are half a generation apart here (`configSnapTouch` vs `configElementSnap`), so a patch
would have to be duplicated per upstream while the two differ only in context and the inserted lines are identical.
That is exactly what used to happen (`0005` / `0006`); a line-by-line comparison showed 24 differing lines, all of
it context drift, with the whole maintenance cost in "regenerate two patches whenever upstream moves".

The insertion script is idempotent (anchor-based, skips existing entries, `--check` reports only), and three trees
were verified byte-identical: `android` upstream + script == the old `0005` final state, `android-cn` upstream +
script == the old `0006` final state, PC baseline + script == `src/src/pc/configfile.c`.

`gen_platform_patches.py` **compares the per-file platform delta computed from both upstreams** and aborts if they
differ — that means the two upstreams have genuinely diverged and the file should be split out into per-target
patches rather than letting a shared patch silently work on only one of them.

The exclusion list is down to these 3 files and exists in both `scripts/gen_platform_patches.py` (`EXCLUDED`) and
`scripts/apply_patches.sh`; the generator asserts they match — **changing one means changing the other**.

Always apply through `scripts/apply_patches.sh` (idempotent); do not hand-write `--exclude`:

```bash
scripts/apply_patches.sh <pc|android|android-cn> <clean upstream checkout> [--frontend]
```

It is not `install.sh`: it neither builds nor packages, it only layers the patches onto an upstream tree, and it can
be called right after `install.sh`.

## Optional patch: 0007-djui-frontend.patch

Touches only `src/pc/djui/djui_panel_misc.c`, adding a "Chinese text pack (iQue)" checkbox under Settings → Other
that switches at runtime and persists the choice.
**Without it everything still works — you just have to flip `chinese_text` in `config.ini` instead** (this is the
UIPatch mentioned in the README).
`config.ini` stores only that one key: whether it can be enabled is decided at startup (is the iQue dump there;
**loading a romhack no longer affects the decision**), and when the check fails the checkbox is greyed out but
`chinese_text` is **not written back** — otherwise running once without the cartridge inserted would silently flip
the player's choice to `false`.

The split boundary is a hard constraint; do not widen it casually:

- `src/pc/djui/djui_panel_confirm.[ch]` belongs to the same group as the panel toggle. It adds
  `djui_panel_confirm_create_ex()` to the stock panel (so even the "No" button can carry a callback). **Note**: the
  first-run confirmation box was replaced by "auto-enable when an iQue ROM is detected" (see `src/pc/pc_main.c`), so
  `_ex` currently has **no call sites**; it is kept only so that restoring a confirmation box later does not require
  touching these files again. If it is decided for good that it is unneeded, deleting the changes to these two files
  has no effect on anything else.
- The `lang/*.ini` string changes are in no group and are not a patch; they are inserted by
  `scripts/add_lang_strings.sh` (see above). `CHINESE_TEXT_PACK` is harmless even without
  `0007-djui-frontend.patch` (it just adds an entry DLANG references).
- `0007-djui-frontend.patch` also applies standalone with `git apply -p1` on a clean baseline (no other group
  touches those three files), so there is no ordering coupling.

It corresponds to `install.sh`'s `--frontend`: `0007-djui-frontend.patch` is applied only when selected. Because it
is optional, **overwriting the final state with `cp -R src/.` is not acceptable** (that would pull in the frontend
unconditionally); either copy only the files covered by the shared groups, or use the order "apply `0001`~`0006` →
apply `0007` if requested → copy `cn_extra`".

## scripts/

| Script | Purpose |
| --- | --- |
| `apply_patches.sh <target> <upstream root> [--frontend]` | **The applier**: picks patches by target, stacks them in order, fills gaps from `cn_extra/`, inserts language strings; idempotent. Use it instead of hand-writing `git apply --exclude` |
| `add_lang_strings.sh <upstream root> [--check]` | Inserts the two "Chinese text pack" strings into `lang/*.ini` by key; shared by all four upstreams, idempotent |
| `add_cn_config.sh <upstream root> [--check]` | Inserts the 3 `configChineseText*` declarations and 3 config-table entries into `src/pc/configfile.c` (the third `--exclude`d drift file); shared by both Android upstreams, idempotent |
| `gen_all_patches.sh <upstream baseline root>` | **Run this after editing `src/`**; generates every group `0001`~`0007` at once and asserts "groups == full diff" (nothing missing, nothing duplicated) |
| `gen_platform_patches.py --pc-base … --android … --android-cn …` | Regenerates `0008-android.patch` (one file for both upstreams), including the three-way merge, conflict resolution, the both-upstreams consistency assertion and a final-state self-check |
| `gen_patches.sh <upstream root> [output] [--only prefix] [--exclude prefix]` | Single-patch generator, filtered by path prefix; `--only`/`--exclude` may repeat (union) |
| `test_install_args.sh` | `install.sh` argument self-test: parsing, error paths, and whether arguments really reach downstream (git/make/gradle stubbed, offline, no compilation). **Run manually on your machine; CI does not run it** |
| `check_patch_integrity.py` | Needs no upstream baseline: asserts each patch's `@@ -a,b +c,d @@` matches its actual line counts (the thing most easily broken after hand-editing `0008-android.patch`), that every `cn_*.h` included by a patch exists in `cn_extra/` (whose symptom is "PC compiles fine, Android CI explodes"), and that `cn_extra/` does not overlap the group patches |

`gen_patches.sh` behaviour (covered by tests): identical files are skipped; a file present in `src/` but absent from
the baseline is a hard error (it belongs in `patches/cn_extra/`); binaries containing NUL bytes are a hard error
(`diff` only says "Files differ" and still exits 1, so without an explicit check that message ends up inside the
patch); when nothing is selected it writes an empty patch file rather than keeping the old one, and the applier skips
empty patches.

## platform/

One directory per platform / package format, holding patches or scripts tied to a specific build environment.

> `install.sh` calls into here in step 6 according to `--package` (or the wizard's answer): `deb` → `DEBIAN/mkdeb.sh`,
> `rpm` → `rpm/mkrpm.sh`, `arch` → `makepkg` in `pacman/`, `mac` → `darwin/mkmac.sh`, `setup` → `windows/mkexe.sh`,
> `zip` → `portable/mkzip.sh`, `other` → just prints the install command (`freedesktop/install.sh`).

| Directory | Contents | Notes |
| --- | --- | --- |
| `platform/DEBIAN/` | `control.in` + `mkdeb.sh` | Debian package metadata and build script |
| `platform/pacman/` | `PKGBUILD` + `.install` | Arch package script |
| `platform/rpm/` | `sm64coopdx-iquedx.spec` + `mkrpm.sh` | RPM for Fedora / RHEL / openSUSE |
| `platform/darwin/` | `Info.plist.in` + `mkmac.sh` | macOS `.app` / `.dmg` / `.pkg` / `.zip` |
| `platform/freedesktop/` | `*.desktop` + icons + `install.sh` | Shared by unpackaged distros: launcher and icons |
| `platform/portable/` | `mkzip.sh` | Portable zip (all three platforms, unzip and play) |
| `platform/windows/` | `sm64coopdx-iquedx.iss` + `mkexe.sh` + `ChineseSimplified.isl` | Inno Setup wizard (`setup.exe`), Windows-only; the language file ships with this repo because the official installer has no Simplified Chinese |

### platform/DEBIAN

`control` is a **template** (`control.in`), not the final file: Debian's `Architecture` accepts exactly one value, so
`amd64, aarch64` is rejected by dpkg, and Debian spells aarch64 as `arm64`. Architecture and version are filled in by
`mkdeb.sh` at packaging time:

```sh
sh platform/DEBIAN/mkdeb.sh                 # payload from <repo root>/dist, version 1.5.1
sh platform/DEBIAN/mkdeb.sh <payload dir> <version>
sh platform/DEBIAN/mkdeb.sh --print         # print the filled-in control only, for review
```

Paths inside the package: `/opt/sm64coopdx-iquedx/` (payload) + `/usr/share/applications/` (launcher) +
`/usr/share/icons/hicolor/256x256/apps/` (icon). Requires `dpkg-deb` (ships with the `dpkg` package).

### platform/pacman

`PKGBUILD` **carries no sources** (`source=()`): `install.sh` has already assembled upstream + patches + cn_extra
into `<repo root>/dist/`, and this directory only packages that into `/opt` following Arch conventions, plus launcher
and icon. `pkgver` must match the upstream version declared in `upstream.txt`; update it when the upstream moves.

### platform/rpm

Also **carries no sources**: the payload is in `<repo root>/dist/`. The spec has no `%prep` / `%build`; the entry
point `mkrpm.sh` first lays out a staging directory in the target layout (`opt/sm64coopdx-iquedx` +
`usr/share/applications` + `usr/share/icons/…`), then uses `--define 'stage …'` so the spec can `cp` straight into
`%{buildroot}`:

```sh
sh platform/rpm/mkrpm.sh                 # payload from <repo root>/dist, version 1.5.1
sh platform/rpm/mkrpm.sh <payload dir> <version>
sh platform/rpm/mkrpm.sh --print         # no packaging; print the staging tree and the rpmbuild command
```

Three switches in the spec must stay off: `debug_package` (there is no source to split), `__os_install_post`
(includes strip and build-id relinking, which would modify the binary), and `AutoReqProv` (auto dependencies record
the build machine's library names, which breaks cross-packaging). Dependencies are split with
`%if 0%{?suse_version}`: openSUSE uses `libSDL2-2_0-0 / libglvnd / libz1 / libcurl4`, everything else uses
`SDL2 / mesa-libGL / zlib / libcurl`. Requires `rpmbuild` (Fedora `dnf install rpm-build`, openSUSE
`zypper in rpm-build`).

### platform/darwin

`mkmac.sh` puts the payload directory **wholesale** into `Contents/MacOS/` — the game looks for `res/` and `lang/`
next to the executable, and moving them into `Resources/` would require code changes; `Contents/Info.plist` is
generated from `Info.plist.in` by filling placeholders:

```sh
sh platform/darwin/mkmac.sh <payload dir> <version>          # default: .app + .dmg (needs hdiutil)
sh platform/darwin/mkmac.sh <payload dir> <version> --zip    # zip from any OS
sh platform/darwin/mkmac.sh <payload dir> <version> --pkg    # .pkg (needs pkgbuild)
sh platform/darwin/mkmac.sh <payload dir> <version> --app-only
```

The icon prefers a full size ladder via `sips` + `iconutil`; without those it degrades to "put a 256×256 PNG into
the `ic08` block of the icns" (macOS 10.7+ accepts PNG-backed icns, single size only). `codesign` is used for an
ad-hoc signature when available — **on Apple Silicon an unsigned arm64 binary is rejected by the kernel outright**;
this is not notarisation, so a downloaded package still hits Gatekeeper once (right-click → Open, or
`xattr -dr com.apple.quarantine`). plist validation uses `plutil -lint` on Darwin and python3's `plistlib`
elsewhere — some distros ship a same-named `plutil` that is the Swift implementation and misreports when given a file
argument.

### platform/freedesktop

For distros that "do not package, just untar into /opt":

```sh
sh platform/freedesktop/install.sh [install root]   # defaults to /opt/sm64coopdx-iquedx
sh platform/freedesktop/install.sh --uninstall
DESTDIR=/tmp/stage sh platform/freedesktop/install.sh <dir>   # install into staging, no system touch, no root
```

`Exec=` is rewritten to the real install path; `Icon=sm64coopdx-iquedx` relies on the same-named PNG being installed
too.

### platform/windows

The Inno Setup wizard: the whole payload goes into `{app}`, with Start Menu / desktop shortcuts, an uninstaller and
an optional Chinese UI.

```sh
sh platform/windows/mkexe.sh                          # payload from <repo root>/dist, version from upstream.txt
sh platform/windows/mkexe.sh <payload dir> <version>
sh platform/windows/mkexe.sh --check                  # only probe whether ISCC exists (used by install.sh)
```

- Windows only: `ISCC.exe` is a native Windows program and does not exist on Linux/macOS. Use `-p zip` elsewhere.
- ISCC lookup order is `$ISCC` → `PATH` → Inno Setup 6's default install location; the default path contains spaces
  and parentheses, so each candidate is tested individually rather than concatenated.
- The `.iss` must be **UTF-8 with BOM**: Inno Setup 6 only parses it as UTF-8 when it sees the BOM, otherwise the
  Chinese UI turns into mojibake **without any compile error**. `mkexe.sh` checks the first three bytes, and one of
  the self-tests guards this.
- Arguments are passed as `/DMyAppVersion` / `/DMySourceDir` / `/DMyOutputDir` / `/DMyCnLang`. Paths must first be
  converted with `cygpath -w`, otherwise ISCC treats `/c/...` as a command-line switch.
- **`export MSYS2_ARG_CONV_EXCL='*'` is mandatory before calling ISCC**: MSYS2 rewrites arguments starting with `/`
  as POSIX paths (`/DMyAppVersion=1.5.1` → `D:/MyAppVersion=1.5.1`), after which ISCC sees a second script filename
  and only says `You may not specify more than one script filename.` Paths are already converted by `cygpath`, so the
  automatic conversion must be disabled entirely.
- **Official Inno Setup has no Simplified Chinese** (`Languages\` holds 26 official languages), which is why the repo
  ships `platform/windows/ChineseSimplified.isl` (taken from jrsoftware/issrc's `Files/Languages/`, UTF-8 + CRLF, no
  BOM). Lookup order: the user's own copy in the compiler directory → the bundled copy → English UI if neither
  exists; a hit is passed as `/DMyCnLang=<absolute path>`.
- When the language file is newer than the compiler, ISCC reports `Unknown message name`; `mkexe.sh` therefore
  **drops the language file and retries once** (English UI), after printing the original error verbatim — an English
  UI beats producing no package at all.
- The CI Windows job additionally does a **silent install → check main binary / dynos / uninstaller → silent
  uninstall**; compiling does not prove it installs, and only this step exercises the `[Files]` recursion and the
  uninstaller.

## GitHub Actions

There is a single pipeline, `build.yml`, with five jobs covering the two desktop platforms × two architectures plus
Android:

| job | Default build options | Notes |
| --- | --- | --- |
| `linux` (`ubuntu-22.04`) | `-c -f -d` | x86_64. First `-p no` to compile only, then `install.sh -po -p all --path build-iquedx/upstream` to produce `.deb` / `.rpm` / portable zip; the Arch package is built inside an `archlinux:latest` container with `makepkg` |
| `linux-arm` (`ubuntu-22.04-arm`) | `-c -f -d` | aarch64, produces only `.deb` / pacman / portable zip (no rpm installed, `-p all` skips it with a warning); the Arch package runs in `menci/archlinuxarm:base-devel` (the official archlinux image is x86_64 only) |
| `windows` (`windows-latest`) | `-c -f -d` | MSYS2 mingw64, produces the Inno Setup wizard (`*-setup.exe`) + portable zip. Inno is installed via `choco install innosetup` and the `ISCC` path is put into `GITHUB_ENV`; if missing, the wizard step only warns and the zip still builds |
| `macos` (matrix: `macos-latest` / `macos-15-intel`) | `-c -f -d` | One dmg + portable zip each for arm64 and x86_64; an extra self-containment check verifies the `.app` does not link back into brew |
| `android` (`ubuntu-22.04`) | `-a -c -f -d` | SDK 33 / build-tools 33.0.2; `install.sh` runs `make TOUCH_CONTROLS=1` to generate resources, then `gradle assembleRelease`, then signs with the upstream's own `platform/android/{key.pk8,certificate.pem}` and uploads |

The "default build options" column only holds for push / PR triggers. Manual runs (`workflow_dispatch`) are rewritten
by three inputs:

| Input | Values | Effect |
| --- | --- | --- |
| `upstream` | localised / stock | Localised → `-c` (PC uses `cn-repo`, Android uses `android-cn-repo`); stock adds nothing |
| `frontend` | checked (default on) | `-f` → additionally applies `0007-djui-frontend.patch`, making the Chinese text pack toggle appear under Settings → Other |
| `djui_modern` | checked (default on) | `-d` → applies the djui_modern module (before `0001`~`0006`). **Only valid with the localised upstream**: the module hard-depends on the localised upstream's `src/pc/djui/cn_glyphs.h`, and "stock + djui_modern" is rejected outright by `install.sh` with an explanation |

Assembly lives in `build.yml`'s top-level `env.IQDX_BUILD_ARGS`, shared by all five jobs. It uses GitHub expressions
rather than shell conditionals, and two traps are one edit away: a boolean `false` is a **falsy value**
(`event.inputs` values are always strings, so `|| default` is required), and a true branch must not expand to an
empty string (`cond && '' || '-c'` gets swallowed by `||`). Verify all seven combinations locally before committing.

**No offline tests run inside the pipeline.** Each job only does "install deps → build → package → upload"; the
argument self-test and the workflow-expression self-test are run locally (`scripts/test_install_args.sh`, see the
table above). The reason is practical: those checks exercise repository scripts rather than the artefact, so
inserting them mid-pipeline only makes one button press take minutes longer while producing a less clear failure than
a local run. The only things worth blocking on in CI are properties of the artefact itself (the `.deb` architecture
field, `.app` not linking back into brew, the Windows wizard installing and uninstalling).

All five jobs share one concurrency group (`build-<ref>`): a push runs one set, and a new push cancels the old one.

**Why `install.sh` runs twice**: GitHub jobs do not share a workspace, only artefacts. `-po/--package-only` exists
for exactly that "the second job has only the artefact" case — it skips clone/patch/build and consumes the compiled
tree pointed to by `--path`; a missing artefact exits `255` (distinct from the `1` used for packaging errors).

## The three destinations for a change

| Change type | Goes to | How it is applied |
| --- | --- | --- |
| Modify an existing upstream file (core) | `src/` (same path) | Falls into one of the `0001`~`0006` groups by responsibility, `git apply -p1` |
| Modify an existing upstream file (optional frontend) | `src/` (same path) | Goes into `0007-djui-frontend.patch`, applied according to `--frontend` |
| Change a language string | Constants in `scripts/add_lang_strings.sh` | Inserted by key at apply time, no patch generated |
| Change the Chinese config entry (Android) | Constants in `scripts/add_cn_config.sh` | Same, inserted by anchor |
| A new file upstream does not have | `patches/cn_extra/` (same path) | Copied into the upstream root per file, gap filling only (existing files skipped) |
| Android platform difference | Three-way merge in `scripts/gen_platform_patches.py` | Generates the shared `0008-android.patch`, `git apply -p1` |
| Per-platform / per-package difference | `platform/<name>/` | Called by install.sh on demand |
